## The eight items (user's words condensed, scoping notes indented)

1. **Sortable columns on the Front bucket table** — click column
   headers to sort: bucket (alphabetical), scope, pending, oldest,
   unanalyzed, etc.
   - Scope: client-side sort in `static/app.js` (CSP: no inline JS) or
     server-side `?sort=` params. Table is small (bucket count) —
     client-side is enough. Sort state must not fight the j/k selection
     model (`rows()` reads DOM order).

2. **Tooltips on the top nav/status bar** — each status item (worker,
   pending, follow-ups, sentinel, miner, report) needs a short plain-
   words explanation on hover.
   - Scope: `title=` attributes (or CSS tooltips) threaded from the
     status model; wording must follow Y-9 (human language, no system
     vocabulary — "the background analyst that pre-reads new lessons",
     not "worker").

3. **Clickable affordance** — anything clickable must be visually
   distinct from plain text; right now some links read as ordinary
   text.
   - Scope: CSS only. The ui-polish pass deliberately muted link
     styling (nav links inherit muted fg, underline on hover only) —
     that judgment call is hereby reversed by user taste: bias toward
     visible affordance (color and/or persistent underline/chevron) on
     every interactive element.

4. **Context-filtered hotkey footer** — the keymap footer is crowded;
   show ONLY the keys usable on the current page ("can't attach or edit
   a note from the front page, so why am I seeing the hotkey").
   - Scope: `keymap.py` already carries per-entry context
     (list/detail/holding/pane/global — the help overlay prints them).
     Filter the FOOTER by the current page's active contexts; the `?`
     overlay stays the full reference (it already says so in the
     footer's own trailing entry).

5. **⚠ SPEC — everything the UI asks the user to run in a terminal must
   be doable from the UI.** Concrete case: the unregistered-project
   notice says "Run `self-learn host add <path>`" — that should be a
   button. User's principle, near-verbatim: *"I should essentially be
   able to do everything I need to do via UI and not have to open a
   terminal."*
   - This DIRECTLY reverses a dated v1 pin: 09 §11 Y-11 — "v1 does
     **not** arm `host add` from the surface: registration is a
     canon-target decision, deliberately human + CLI (10 §4 row)."
     The user's standing principle supersedes the pin's rationale (the
     human IS deciding — the UI is just the hand). Needs: a dated Y-11
     amendment + 10 §4 row edit, then an armed host-add action through
     the same arm/confirm verb runner as every other mutation. Sweep
     for OTHER copyable-command surfaces while at it (the settings.json
     hook-registration snippet, sentinel instructions, anything in
     error strips).

6. **Desktop icon / launcher entry** — people should open the app
   intuitively, not via a shell command.
   - Scope: ship a `.desktop` file (Exec=self-learn-ui-open, proper
     Icon=, StartupWMClass matching the T-D title-match reality — recall
     chromium --app on Wayland derives app_id from the URL) installed by
     install.sh into `~/.local/share/applications/`; an SVG/PNG icon
     asset in the product repo. Fuzzel/wofi/rofi pick it up from there.

7. **⚠ SPEC — conversational agent pane on Bucket AND Detail, with
   verbs.** A chat window at bucket level and per-record. The agent
   must be system-aware (knows the buckets, the lesson under review,
   routing doctrine — "the contexts it should be ready to talk to me
   about") and must be able to ACT, not just chat: *"if I tell it to
   route to a different bucket, for example, it should be able to do
   that."*
   - Today's pane is Detail-only Iterate, and its charter deliberately
     denies resolution verbs ("agent iterates, only the human routes" —
     07/09). The user's directive refines rather than repeals the
     invariant: the HUMAN still decides, but a typed instruction in
     chat is a valid decision channel, with the agent as executor.
     Needs spec work before build: (a) charter expansion — which verbs
     the pane agent may invoke, and whether verb calls echo through the
     existing arm/confirm surface (recommended: agent proposes → the
     armed bar renders → human confirms, preserving the arm/confirm
     spine and the scan/refusal path); (b) a bucket-level pane variant
     with bucket context (list of records, cluster/bulk state);
     (c) system-context prompt authoring (doctrine §8 register applies:
     pane prose renders to the decision-maker, jargon is a defect);
     (d) serialization rules — bucket pane vs record pane vs verb
     runner (today: one pane, verbs serialized, interrupt-first).
     This is the heftiest item; it is effectively G-3's second act.

8. **Front page must surface deferred items per bucket** — the bucket
   walk shows pending/oldest/unanalyzed but not whether a bucket holds
   deferred records.
   - Scope: `status/list` data already knows deferral (the report JSON
     carries a `deferred` list; the user bucket showed `deferred: 1`
     in dev). Add a Deferred column (or a badge on the bucket row) to
     the Front model + template.
