## Items (user's words condensed; root causes verified in code)

1. **Failed registration error is unreadable — flashes then vanishes.**
   Root cause, refusal side: `self-learn host add
   /home/komi/repos/keyboards` exits non-zero because the path is not
   a git repo (hosts.py "canon hosts must be committable"); the
   confirm route renders the stderr into the bar
   (routes.py `host_add_confirm`, error leg → `host_add_bar.html`
   error strip). Root cause, vanish side: NOT YET PINNED — something
   re-swaps the bar right after the error render (candidates: an SSE
   `refresh` re-render of the region, or the any-key-disarms handler
   firing on the post-confirm keyup). The fix must make the error
   PERSIST until the user dismisses or re-arms — and even then, raw
   CLI stderr ("canon hosts must be committable") violates the Y-9
   plain-words rule for this surface; the failed-registration leg
   needs a human sentence, with stderr demoted to detail.

2. **Registering a non-git project should offer git init, disclosed
   up front (user directive).** A project can be plain text and still
   deserve registration; the git requirement exists because canon
   writes are commits (audit / rollback / recompile all diff against
   git). Ruling: keep the committability invariant, make the UI flow
   absorb the gap — when the registration target is not a git repo,
   the ARM state must say clearly that **a git repository will be
   created (`git init`) as part of registering**, and the confirm
   performs init + `host add` in one motion. User's words: *"make it
   clear that a git init will be performed when a user chooses to
   register a new project that isn't already a repo through the UI."*
   Design note: decide where the init lives (CLI `host add --init`
   flag vs UI-side pre-step) at spec time — the CLI flag keeps the
   UI a thin caller and gives the terminal user the same affordance.

3. **Record re-home + umbrella-project routing judgment (user
   directive).** The bucket a lesson lands in is fixed at capture
   time from the session cwd; neither the analyst nor the human can
   move a record to another project afterward. The user wants the
   opposite of the narrow default here: *"anything that got
   registered as a lesson for zmk-config-offsetkey should have been
   registered under repos/keyboards… i'd like it to be a bit smarter
   about this and make choices the way that I would."* Two-part item,
   spec-gated:
   - **Mechanism**: a re-home move (new CLI verb; analyst-proposable
     through the existing proposal/arm spine; human confirms) that
     relocates a pending record to another registered bucket.
   - **Judgment**: routing-doctrine amendment — when a lesson's
     firing range extends beyond its repo (this one triggers on
     Hyprland/makima/keyd/xkb host configs, not just the zmk repo),
     prefer the nearest registered ANCESTOR project; this is the
     existing "narrowest surface that still fires" rule applied
     honestly, not a new bias. All three analyst consumers (M2
     worker, review session, chat pane) compile from the one doctrine
     file, so the judgment lands everywhere at once.
