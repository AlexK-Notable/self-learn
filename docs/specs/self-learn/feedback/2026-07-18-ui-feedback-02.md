## Items (user's words condensed; root causes verified in code)

1. **"Open bucket chat" doesn't seem to do anything** — and item 5,
   same walkthrough: *"ah, wait, the window for the chat just opened.
   there was no indication that anything was happening after i
   clicked the button. it should pop open the interaction window and
   let it have some kind of loading message or stream the response or
   something."* Root cause: `PaneManager.start()` AWAITS the whole
   first agent turn (30–90 s real model) and the split only renders
   from the POST response — the SSE deltas stream the entire time,
   but the client has no pane region to put them in until the POST
   returns. **Fix B**: start returns the split immediately in a
   "starting" state; the first turn drains as a background task; the
   existing SSE stream fills the live region. (Dated 09 §4.2 / 10 §1
   amendment — its own spec gate before build.)
2. **Project registration from the UI: worked.** (Round 1 item 5
   confirmed live by its user.)
3. **Approve → confirm on a project record errored:** `self-learn
   route: skill-md destination needs skill:<name> scope, got
   'project' — use claude-md or reference`, with no path forward
   visible. Root cause: the analyst proposal suggested `skill-md` for
   a project-scoped record and the UI's destination cycle
   (`cycle_destination`) offers the same three destinations
   regardless of scope — the UI armed a combination the CLI has
   always refused. The stderr-verbatim error strip is pinned (09 §5 —
   the server adds no interpretation), so the fix is PREVENTION, not
   error rewriting. **Fix A**: scope-filter the destination set
   (skill-md only inside a skill bucket) everywhere a destination is
   offered or defaulted — the `o` cycle, the Approve default (a
   scope-invalid analyst suggestion is corrected to a valid default
   with a visible plain-words note), and the pane proposal intake
   (`validate_proposal` refuses skill-md from non-skill scopes so the
   agent is taught at proposal time, not the human at confirm time).
   Immediate workaround given to the user: press `o` to cycle to
   claude-md/reference, then Approve.
4. **Defer: worked.**
5. (Merged into item 1 — same root cause.)
6. **Window placement (added from the overnight run's own
   observation, ratified by the user):** the launcher opens the app
   window on DP-1 — the user's rule is DP-2, never DP-1; it had to be
   moved by hand twice. **Fix C**: launcher-only
   `SELF_LEARN_UI_MONITOR` env var — when set (and hyprctl present),
   the launcher focuses the window (fresh or existing) and moves it
   to that monitor; unset = today's behavior. Host-side value for
   this machine to be wired after merge (environment.d +
   set-environment), not hardcoded in the product.
